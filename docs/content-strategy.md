# コンテンツ戦略 — aiaiai

## 概要

aiaiaiのコンテンツ戦略は「公式一次情報を正確に・実務者が判断できる形に再構成して届ける」ことを軸とする。ニュース転載ではなく、情報の構造化と重複統合により「結局何を読めばいいか」を明確にする。

---

## 1. コンテンツタイプ

### 1.1 アップデート要約記事（Update Summary）

もっとも基本的なコンテンツ単位。公式リリースノート・changelog・GitHub Releasesから生成する。

| 項目 | 内容 |
|---|---|
| 対象 | 各プロダクトの個別アップデート |
| 生成トリガー | 収集パイプラインが新規RawItemを取得し、TopicClusterに統合後 |
| 更新頻度 | 日次（Cron実行ごと） |
| URL例 | `/article/chatgpt-2026-02-27-voice-mode-update` |

### 1.2 比較記事（Comparison Article）

同一テーマで複数プロダクトにまたがる更新がある場合に生成する横断比較コンテンツ。

| 項目 | 内容 |
|---|---|
| 対象 | 同一テーマの複数プロダクト更新（例: 各社のコンテキストウィンドウ拡張） |
| 生成トリガー | 管理者による手動作成、または同一Tagに2プロダクト以上が紐づいた場合に候補表示 |
| 更新頻度 | 不定期 |
| URL例 | `/compare/context-window-expansion-2026-02` |

### 1.3 週次ダイジェスト（Weekly Digest）

1週間分のアップデートを重要度順にまとめた定期コンテンツ。

| 項目 | 内容 |
|---|---|
| 対象 | 過去7日間に公開された全Article |
| 生成トリガー | 毎週月曜 AM 9:00（JST）に自動生成 |
| 構成 | トップ3ハイライト → プロダクト別まとめ → 今週のアクション |
| URL例 | `/weekly/2026-w09` |

## 2. 要約構造（Summary Structure）

すべてのアップデート要約記事は、以下の統一構造で生成する。読者が一覧ページのカードだけで判断できることを目標とする。

### 2.1 3行要約（summary3）

記事カードに表示する最小単位。3行以内で以下を伝える。

```
1. 何が変わったか（What Changed）
2. 誰に影響するか（Who Is Impacted）
3. 何をすべきか（Recommended Action）
```

**例:**
```
1. ChatGPT Plusにリアルタイムウェブ検索が標準搭載された
2. Plus/Team/Enterpriseユーザー全員に影響
3. プラグイン「WebPilot」を使用中の場合は移行を検討
```

### 2.2 詳細要約（summaryLong）

記事ページ冒頭に表示する段落形式の要約。200〜400文字程度。技術的背景・文脈を含む。

### 2.3 構造化セクション

記事本文は以下のセクションで構成する。

| セクション | フィールド名 | 内容 |
|---|---|---|
| 何が変わったか | `whatChanged` | 変更内容の具体的記述。差分ベースで記載 |
| 誰に影響するか | `whoImpacted` | 影響を受けるユーザー層・プラン・利用形態 |
| 推奨アクション | `actions` | 読者が取るべき具体的行動のリスト |
| 出典 | `sources` | 元記事へのリンク一覧（公式優先） |

### 2.4 アクション判定ラベル（Try / Monitor / Ignore）

各記事に対して、読者の行動指針を1つ付与する。

| ラベル | 意味 | 付与基準 |
|---|---|---|
| **Try** | すぐに試す価値がある | 新機能リリース、無料で利用可能、業務改善に直結 |
| **Monitor** | 動向を注視すべき | ベータ版、段階ロールアウト、破壊的変更の予告 |
| **Ignore** | 大多数に影響なし | マイナーバグ修正、限定地域のみ、ニッチな用途 |

このラベルはスコアリング結果と連動し、自動付与後に管理者が確認・修正できる。

## 3. 引用ポリシー（Citation Policy）

### 3.1 基本原則

| ルール | 詳細 |
|---|---|
| **全文転載禁止** | 元記事の全文をそのまま掲載することは一切行わない |
| **要約主体** | 独自に再構成した要約を主コンテンツとする |
| **出典明記** | すべての記事に元情報のURL・タイトル・公開日を明記する |
| **必要最小限の引用** | 引用は事実確認・正確性担保に必要な最小範囲に限定する |

### 3.2 著作権法「引用」要件の遵守

日本の著作権法第32条に基づく「引用」の要件を厳守する。

1. **公表された著作物**であること
2. **公正な慣行**に合致すること
3. **正当な範囲内**であること（主従関係: 自サイトの記述が「主」、引用が「従」）
4. **出所の明示**があること

### 3.3 引用の実装ルール

```
- 引用部分は <blockquote> + cite属性で明確に区別する
- 引用は原則として連続3文以内、200文字以内
- 引用の前後に自サイト独自の解説・分析を必ず配置する
- 画像・図表の転載は原則禁止（リンクで代替）
```

### 3.4 出典表示フォーマット

```markdown
出典: [記事タイトル](URL) — サイト名（YYYY-MM-DD）
```

## 4. SNS隔離ラベルポリシー

### 4.1 背景

X（Twitter）上の情報は速報性が高い一方、誤情報・推測・リークを含む可能性がある。公式発表前の情報を同列に扱うと、サイト全体の信頼性を毀損する。

### 4.2 隔離ラベルの定義

| ラベル | 状態 | 表示 | 説明 |
|---|---|---|---|
| `unverified` | 未検証 | 「速報（未検証）」バッジ | 公式情報で裏取りが完了していない |
| `verified` | 検証済み | バッジなし（通常記事に昇格） | 公式情報と紐づけが完了 |
| `retracted` | 撤回 | 「撤回済み」バッジ | 誤情報と判明し非公開化 |

### 4.3 運用フロー

```
1. X経由の情報を取得 → 自動的に unverified ラベルを付与
2. 一覧ページでは「速報（未検証）」バッジ付きで隔離表示
3. 公式情報が確認された場合 → verified に昇格、TopicClusterに統合
4. 誤情報と判明した場合 → retracted に変更、記事を非公開化
5. 48時間以上 unverified のままの場合 → 管理者にアラート通知
```

### 4.4 表示ルール

- 未検証記事は一覧ページで通常記事より下位に表示する
- 未検証記事のカードには黄色の「速報（未検証）」バッジを常時表示する
- 検索結果では未検証記事をデフォルトで除外し、フィルターで表示可能にする

## 5. 品質保証ワークフロー（QA Workflow）

### 5.1 パイプライン全体像

```
[自動生成] → [下書き] → [管理者レビュー] → [公開] → [継続監視]
```

### 5.2 各フェーズの詳細

#### Phase 1: 自動生成（Auto-Generate）

| ステップ | 処理内容 |
|---|---|
| 収集 | Fetcher がソースから RawItem を取得 |
| 正規化 | URL正規化、タイトル正規化 |
| 重複統合 | 同一トピックの RawItem を TopicCluster に統合 |
| 要約生成 | テンプレートベースで summary3 / summaryLong / whatChanged / whoImpacted / actions を生成 |
| スコアリング | 信頼度・有用性・重要度・新規性・緊急性の5軸でスコア算出 |
| ラベル付与 | スコアに基づき Try / Monitor / Ignore を自動付与 |
| ステータス | `draft`（下書き）として保存 |

#### Phase 2: 管理者レビュー（Admin Review）

管理画面 `/admin/articles` で以下を確認・修正する。

| 確認項目 | チェック内容 |
|---|---|
| 要約の正確性 | 元情報と要約の整合性 |
| 引用の適切性 | 引用範囲・出典表示が基準を満たしているか |
| ラベルの妥当性 | Try / Monitor / Ignore が適切か |
| タグの正確性 | プロダクト・テーマ・レベル・ユースケースのタグが正しいか |
| 重複統合の妥当性 | TopicCluster の統合が正しいか |
| SNS隔離 | 未検証情報が混入していないか |

#### Phase 3: 公開（Publish）

- 管理者が `approve` ボタンで `published` ステータスに変更
- 公開と同時にsitemap.xmlを更新
- OGP/JSON-LDメタデータが正しく出力されることを自動検証

#### Phase 4: 継続監視（Continuous Monitoring）

| 監視項目 | 対応 |
|---|---|
| 元記事の更新 | contentHashの変化を検知し、要約の再生成を提案 |
| 削除依頼 | LegalEventとして記録し、即時非公開化 |
| 誤情報報告 | 管理者に通知、確認後に修正または撤回 |
| リンク切れ | 定期チェックで検知、管理者に通知 |

### 5.3 ステータス遷移

```
draft → published → archived
  ↓        ↓
retracted  unpublished
```

| ステータス | 意味 |
|---|---|
| `draft` | 自動生成直後、レビュー待ち |
| `published` | 公開中 |
| `unpublished` | 管理者が非公開にした |
| `retracted` | 誤情報・削除依頼により撤回 |
| `archived` | 古くなったため保管（検索可、一覧非表示） |

## 6. コンテンツ品質基準

### 6.1 記事品質チェックリスト

- [ ] 3行要約が「何が・誰に・何をすべきか」の構造になっている
- [ ] 出典URLが有効で、公式ソースが含まれている
- [ ] 引用は200文字以内、blockquoteで明示されている
- [ ] Try / Monitor / Ignore ラベルが付与されている
- [ ] 適切なタグ（プロダクト・テーマ・レベル）が設定されている
- [ ] SNS由来の情報は隔離ラベルが付与されている

### 6.2 禁止事項

- 元記事の全文コピー
- 出典なしの情報掲載
- 画像・図表の無断転載
- 推測を事実として記載
- SNS上の未検証情報を公式情報と同列に扱うこと
