## 1. MVPの定義と目標

### 1.1 MVPとは何か

本プロジェクトにおけるMVP（Minimum Viable Product）は、**最小限の機能で「aiaiaiの核心的価値」を検証できるプロダクト**を指す。

aiaiaiの核心的価値とは以下の3点である:

1. **一次情報の自動集約**: 公式リリースノート・changelog・GitHub Releasesを日次で自動収集し、手動巡回を不要にする
2. **重複統合と優先順位付け**: 同一トピックの複数ソースを1本に束ね、「読む価値順」で提示する
3. **実務判断できる日本語要約**: 「何が変わったか・誰に影響するか・今すぐ何をすべきか」を一覧だけで把握できる

MVPは「ニュース転載サイト」ではなく、**公式一次情報を最優先に収集し、実務者向けに再構成する情報インフラ**の最小実証版である。

### 1.2 MVPの目標

| # | 目標 | 説明 |
|---|---|---|
| G1 | 日次自動収集の実現 | Vercel Cron Jobsで1日1回以上、対象ソースから更新情報を自動取得する |
| G2 | 重複統合の実証 | 同一トピックを複数ソースから検出し、Topic Clusterとして1本に束ねる |
| G3 | 実務者向け要約の生成 | 3行要約・差分・影響範囲・推奨アクションを含む構造化要約を生成する |
| G4 | 「読む価値順」の提示 | スコアリングにより信頼性・重要度・実務有用性を加味した順序で表示する |
| G5 | 管理運用の成立 | 管理画面で承認/非公開/要約再生成/ソース停止/クラスタ統合が可能 |
| G6 | SEO基盤の構築 | 検索エンジンからの発見性を初期から担保する |
| G7 | 法務・運用安全性の確保 | 全文転載禁止・X規約遵守・削除依頼対応・監査ログが実装として成立する |

### 1.3 MVPで検証する仮説

| 仮説 | 検証方法 |
|---|---|
| AI実務者は公式一次情報の集約に価値を感じる | 公開後のアクセス数・滞在時間 |
| 重複統合により「結局どれを読めばいいか」が解決する | Topic Cluster経由の閲覧率 |
| 3行要約＋推奨アクションで一覧だけで判断できる | 記事詳細への遷移率（低いほど一覧で完結） |
| スコアリングが実務者の関心と一致する | トップ表示記事のクリック率 |

## 2. MVP対象機能（スコープ内）

### 2.1 情報収集（Ingestion）

#### 2.1.1 日次自動収集（Vercel Cron）

- **実行方式**: Vercel Cron Jobs（`vercel.json`でスケジュール定義）
- **実行頻度**: 日次（毎日 05:00 UTC = 14:00 JST を基本とし、vercel.jsonに定義）
- **エンドポイント**: `api/cron/daily/route.ts`
- **処理フロー**: Fetch → Parse → Normalize → Dedupe/Cluster → Enrich → Summarize → Score → Publish
- **失敗時**: リトライ（最大3回、指数バックオフ）、失敗ログをJobRunに記録
- **手動実行**: `api/ingest/manual/route.ts` で管理画面から任意タイミングで実行可能

#### 2.1.2 対象ソース（MVP）

MVPでは以下の **5プロダクト** を対象とし、公式一次情報を最優先で取り込む。

| 監視対象 | ソース種別 | 具体的URL/取得方式 | 優先度 |
|---|---|---|---|
| **ChatGPT / UI更新** | 公式リリースノート（日本語） | `help.openai.com/ja-jp/articles/6825453-*` / HTML取得 | P0 |
| | 公式リリースノート（英語） | `help.openai.com/en/articles/6825453-*` / HTML取得 | P0 |
| **OpenAI Developers / API** | Developers changelog | `developers.openai.com/changelog/` / RSS | P0 |
| | API changelog | `developers.openai.com/api/docs/changelog/` / HTML取得 | P0 |
| | GitHub Releases（SDK等） | GitHub REST API（`openai/openai-python`等） | P0 |
| **Claude Developer Platform** | Release notes | `platform.claude.com/docs/en/release-notes/overview` / HTML取得 | P0 |
| **Claude Code** | 公式CHANGELOG | `github.com/anthropics/claude-code/blob/main/CHANGELOG.md` / GitHub API | P0 |
| | GitHub Releases | `github.com/anthropics/claude-code/releases` / GitHub REST API | P0 |
| **Gemini** | 公式アップデートハブ | `blog.google/products-and-platforms/products/gemini/` / HTML/RSS | P0 |
| | アプリリリースノート（日本語） | `gemini.google/jp/release-notes/` / HTML取得 | P0 |
| | Gemini API changelog | `ai.google.dev/gemini-api/docs/changelog` / HTML取得 | P1 |

#### 2.1.3 X（Twitter）最小実装（規約準拠）

- **絶対遵守**: X利用規約（2026-01-15版）に基づき、スクレイピングは一切行わない
- **許可される取得方式**: X API（公式）または埋め込み表示のみ
- **MVP実装範囲**:
  - 各プロダクトの公式Xアカウントの最新投稿IDの差分取得（X API経由）
  - 投稿内のリンク抽出（公式ブログ/changelogへのリンク検出）
  - 取得した情報は「速報」ラベルで隔離し、公式一次情報に紐づいた場合のみ昇格
- **MVPで実装しない**: ユーザー投稿の収集、感情分析、引用リポスト追跡

#### 2.1.4 GitHub REST API対応

- **レート制限対応**: 未認証60回/時を前提とし、以下を実装
  - `X-RateLimit-Remaining` ヘッダの監視
  - レート制限到達時の指数バックオフ（初回1秒、最大60秒）
  - `304 Not Modified`（ETag/If-Modified-Since）によるキャッシュ活用
  - ページネーション対応（`per_page=100`、`Link`ヘッダ解析）
- **二次レート制限対応**: 短時間の大量リクエストを避けるリクエスト間隔制御（最低1秒間隔）

### 2.2 データ処理パイプライン

#### 2.2.1 正規化（Normalize）

| 対象 | 処理内容 |
|---|---|
| URL | `utm_*`等のトラッキングパラメータ除去、末尾スラッシュ統一、短縮URL解決、プロトコル統一（https） |
| タイトル | 全角半角統一、絵文字・装飾文字除去、記号正規化、前後空白除去 |
| 日時 | UTC基準に統一（ISO 8601）、タイムゾーン情報の保持 |
| コンテンツ | contentHashの生成（SHA-256）、全文は保持しない（転載回避） |

#### 2.2.2 重複統合（Topic Cluster）

MVPでは以下の2段階で重複を判定し、Topic Clusterに束ねる。

| 段階 | 判定方式 | 閾値/条件 | 備考 |
|---|---|---|---|
| **強一致** | canonicalUrl完全一致 | 完全一致 | 最優先。同一URLの異言語版も含む |
| **中一致** | 正規化タイトルのトークン類似度（Jaccard係数） | >= 0.7 | 保守的に判定し、誤結合を防ぐ |

**代表記事の決定ルール**（ヒエラルキー固定）:

```
公式一次情報（official） > 準一次情報（semi-official） > 二次情報（secondary） > SNS（social）
```

同ランクの場合は、日本語ソース > 英語ソース > その他の優先順位とする。

**P1で追加予定**: 弱一致（要約/本文のベクトル埋め込みによる意味類似度判定）

#### 2.2.3 日本語要約生成（Summarize）

各記事について以下のフィールドを生成・保存する。

| フィールド | 内容 | 表示先 |
|---|---|---|
| `summary3` | 3行要約（一覧で完結する簡潔な説明） | 一覧ページ |
| `summaryLong` | 詳細要約（記事ページ用の包括的な説明） | 記事詳細ページ |
| `whatChanged` | 何が新しいか（差分の明確な記述） | 記事詳細・一覧バッジ |
| `whoImpacted` | 誰に影響があるか（職種/レベル/プロダクト） | 記事詳細・フィルタ |
| `actions` | 推奨アクション（Try / Monitor / Ignore） | 一覧バッジ・記事詳細 |
| `useCases` | 実務でどう使えるか（ユースケース） | 記事詳細 |

**MVP要約方式**: テンプレートベースの構造化要約（LLM APIは未指定のため、MVPではルールベース＋テンプレートで生成し、管理画面で承認/修正する運用）

**将来（P1）**: LLM API連携による自動要約生成（Claude/OpenAI/Gemini等、利用先は未指定）

#### 2.2.4 スコアリング（Score）

「読む価値スコア」（0〜100）を算出し、表示順序・おすすめに活用する。

| 指標 | 説明 | 初期重み | データソース |
|---|---|---|---|
| 信頼性 | 公式 > 準一次 > 二次 > SNS | 0.30 | Source種別 |
| 実務有用性 | 業務導線に直結するか | 0.25 | 要約ラベル・テーマ判定 |
| 重要度 | 料金/規約/API変更 > UI改善 | 0.20 | テーマ分類 |
| 新規性 | 初出/破壊的変更の有無 | 0.15 | 差分情報・重複判定 |
| 緊急度 | 今週中の対応要否 | 0.10 | ルールベース判定 |

**補正要因**（ボーナス）:
- 日本語対応/日本展開に関する更新: +5pt
- 破壊的変更（breaking change）: +10pt
- 料金変更: +10pt

合計スコアは `Σ(指標スコア × 重み) + 補正` で算出し、0〜100にクリップする。

### 2.3 公開ページ

#### 2.3.1 ページ一覧と機能

| パス | ページ名 | MVP機能 |
|---|---|---|
| `/` | トップページ | 「読む価値順」で上位記事を表示、プロダクト別セクション、最新更新ハイライト |
| `/latest` | 最新一覧 | 時系列順の全記事一覧、ページネーション、フィルタ（プロダクト/テーマ/レベル/期間） |
| `/article/[slug]` | 記事詳細 | 詳細要約、差分、影響範囲、推奨アクション、原典リンク、関連記事、ソース一覧 |
| `/search` | 検索 | 全文検索（タイトル＋要約＋タグ）、複合フィルタ、ソート（新着/読む価値/重要度/信頼度/緊急度） |
| `/products/[slug]` | プロダクト別ハブ | プロダクト単位の更新一覧（例: `/products/chatgpt`）、最新/重要順切替 |
| `/topics/[slug]` | トピック別ページ | Topic Cluster単位の詳細（代表記事＋関連ソース一覧＋タイムライン） |
| `/weekly` | 週次ダイジェスト | 過去1週間の重要更新まとめ、プロダクト別ハイライト、今週のアクション |
| `/compare` | 比較ページ | プロダクト横断の機能比較表（ChatGPT vs Claude vs Gemini の最新状況） |

#### 2.3.2 検索・フィルタ仕様

| 機能 | MVP実装 | 備考 |
|---|---|---|
| 全文検索 | PostgreSQL FTS（`to_tsvector` / `to_tsquery`） | タイトル＋要約＋タグを対象 |
| プロダクトフィルタ | ChatGPT / OpenAI API / Claude / Claude Code / Gemini | タグ軸: product |
| テーマフィルタ | Update / Pricing / Policy / Security / How-to | タグ軸: theme |
| レベルフィルタ | L1（活用） / L2（定着/自動化） / L3（実装） | タグ軸: level |
| 期間フィルタ | 今日 / 今週 / 今月 / カスタム範囲 | publishedAtベース |
| ソース種別フィルタ | 公式のみ / GitHub / X速報含む | Source種別ベース |
| ソート | 新着順 / 読む価値順 / 重要度順 / 信頼度順 / 緊急度順 | スコアフィールド利用 |

#### 2.3.3 タグ・カテゴリ設計（4軸）

| 軸 | 目的 | MVP値の例 | UI上の表示 |
|---|---|---|---|
| **プロダクト軸** (product) | どのAIプロダクトか | ChatGPT, OpenAI API, Claude, Claude Code, Gemini, Gemini API | グローバルナビ、ハブページ |
| **テーマ軸** (theme) | どんな種類の更新か | Update, Pricing, Policy, Security, Performance, New Feature, Deprecation | フィルタ、タグバッジ |
| **レベル軸** (level) | 誰向けの深さか | L1（活用）, L2（定着/自動化）, L3（実装） | バッジ、フィルタ |
| **実務用途軸** (usecase) | どの業務に関係するか | 経営判断, 企画/マーケ, 開発/実装, CS/サポート, 法務/コンプラ | フィルタ、レコメンド |

### 2.4 管理画面

#### 2.4.1 画面一覧と機能

| パス | 画面名 | MVP機能 |
|---|---|---|
| `/admin` | ダッシュボード | 直近のジョブ実行状況、未承認記事数、エラー件数、ソース稼働状況サマリ |
| `/admin/sources` | ソース管理 | ソースの追加/編集/停止/削除、取得方式（RSS/HTML/GitHub/X）の設定、取得頻度の設定、信頼スコアの設定、規約メモの記録 |
| `/admin/articles` | 記事管理 | 記事一覧（ステータスフィルタ付き）、承認/非公開/削除、要約の再生成トリガー、タグの手動修正、重複統合候補の表示と手動マージ |
| `/admin/jobs` | ジョブ管理 | 実行履歴の一覧（成功/失敗/実行中）、失敗ログの詳細表示、手動再実行ボタン、バックオフ状態の確認 |
| `/admin/settings` | 設定 | SEO設定（デフォルトtitle/description）、法務/運用設定（削除依頼対応フロー）、監査ログの閲覧 |

#### 2.4.2 記事ワークフロー

```
取得(Raw) → 要約生成 → [draft] → 管理者承認 → [published] → 公開
                                  ↓
                            [rejected] → 非公開
                                  ↓
                            [archived] → アーカイブ
```

- 自動100%公開はしない（誤要約・法務・信頼性リスクの吸収）
- 管理者が承認して初めて `published` ステータスとなり公開ページに反映
- 非公開/削除は即時反映

#### 2.4.3 重複統合（クラスタマージ）

- 管理画面で重複統合候補を提示（自動検出＋手動確認）
- 代表記事の切り替え（公式ソースを優先）
- 関連リンクの整備（同一Topic Cluster内の全ソースを表示）

### 2.5 SEO基盤

| 要素 | MVP実装内容 |
|---|---|
| **robots.txt** | `/robots.txt` を静的ファイルとして配置。クロール制御を定義。インデックス除外が必要な場合は `noindex` メタタグで対応（robots.txtはインデックス除外の仕組みではないため） |
| **sitemap.xml** | `api/sitemap/route.ts` で動的生成。全公開記事・プロダクトページ・トピックページのURLを含む。robots.txtにsitemapのURLを記載 |
| **canonical** | 各ページに `<link rel="canonical">` を設定。重複URLの統合を担保。記事ページは正規URLを明示 |
| **OGP** | Open Graph（`og:title`, `og:description`, `og:image`, `og:url`）および Twitter Card（`twitter:card`, `twitter:title`, `twitter:description`）を全ページに設定 |
| **Article JSON-LD** | 記事詳細ページに `Article` 構造化データをJSON-LD形式で埋め込み。`headline`, `datePublished`, `dateModified`, `author`, `description` を含む |

### 2.6 法務・運用安全機能

| 機能 | MVP実装内容 |
|---|---|
| **全文転載禁止** | RawItemに全文を保持しない。要約主体＋出典明記＋必要最小限の引用で運用 |
| **引用要件遵守** | 引用部分の明確な区別（blockquote等）、出所の明示、正当な範囲の遵守 |
| **X規約遵守** | スクレイピング実装を一切含まない。API/埋め込みのみの取得ロジック |
| **robots.txt尊重** | 外部サイトのrobots.txtを取得・解析し、禁止パスへのアクセスを回避 |
| **削除依頼対応** | LegalEventモデルで削除依頼を記録。記事単位で即時非公開/削除/ソース停止が可能 |
| **誤情報隔離** | X経由の速報は「速報」ラベルで隔離。公式一次情報に紐づいた場合のみ昇格 |
| **監査ログ** | AuditLogモデルで法務リクエスト・削除・ソース遮断・ステータス変更をすべて記録 |

### 2.7 テスト

| 種別 | MVP範囲 | 具体例 |
|---|---|---|
| **ユニットテスト** | 正規化/重複判定/スコア算出 | URL正規化（utm除去、スラッシュ統一）、Jaccard係数計算、スコア合成 |
| **収集テスト** | 各Fetcher/Parser | 公式1ソースにつき最低1テストケース（レスポンスモック） |
| **E2E（最小）** | Top/検索/記事/管理 | cron実行 → 記事生成 → 承認 → 公開ページ反映 |

### 2.8 seedデータ

- **目的**: UIと管理画面が成立する状態を初期データで構築する
- **内容**:
  - 5プロダクト分のSourceレコード
  - 各プロダクト3〜5件のサンプルRawItem
  - Topic Clusterのサンプル（重複統合の実例）
  - 公開可能なArticleレコード（要約・スコア付き）
  - 4軸のTagレコード一式
- **用途**: 開発時のUI確認、テストの再現、デモ

## 3. スコープ外（P1/P2）

### 3.1 P1（MVP直後に着手、1〜2ヶ月以内）

| 機能 | 概要 | MVP除外理由 |
|---|---|---|
| **ニュースレター配信** | 週次ダイジェストのメール配信（手動 → 自動） | メール配信基盤の構築が必要。MVPでは `/weekly` ページで代替 |
| **RSS配信** | `/latest` のRSS/Atom フィード生成 | 優先度はあるがMVP必須ではない |
| **LLM自動要約** | Claude/OpenAI/Gemini API連携による自動要約生成 | LLM利用先が未指定。MVPではテンプレート＋手動承認で運用 |
| **意味類似度による重複判定** | ベクトル埋め込みによる弱一致判定 | 精度向上には有効だが、MVP段階ではURL一致＋タイトル類似で十分 |
| **媒体系ソース追加** | ITmedia AI＋、Publickey等の二次情報源 | MVPは公式一次情報に集中。二次情報は優先度を下げる |
| **公開API（読み取り専用）** | 検索/記事/トピックのJSON API公開 | 外部連携は利用者が増えてから |
| **モニタリング/アラート** | ジョブ失敗・レート制限超過のSlack/メール通知 | MVPでは管理画面でのログ確認で代替 |
| **多言語対応強化** | 英語版ソースの日本語自動翻訳 | LLM連携と合わせてP1で実装 |

### 3.2 P2（3ヶ月以降、ユーザーフィードバックを反映）

| 機能 | 概要 | MVP除外理由 |
|---|---|---|
| **会員機能** | ユーザー登録、ログイン、プロフィール | MVPは匿名閲覧のみ。会員機能は利用者数を見て判断 |
| **保存・通知** | 記事の保存、フォロープロダクトの通知 | 会員機能が前提 |
| **パーソナライズ推薦** | 閲覧履歴に基づくおすすめ記事 | 会員機能＋行動データ蓄積が前提 |
| **Slack/LINE連携** | 重要更新のWebhook通知 | 外部連携基盤の構築が必要 |
| **AIチャットナビ（RAG）** | サイト内情報を対象としたAIチャット検索 | ベクトルDB＋RAG基盤の構築が必要。技術的複雑度が高い |
| **法人向けダッシュボード** | 企業単位のカスタムフィード、チーム共有、レポート | BtoBモデルの検証後。収益モデルとセットで設計 |
| **公開API（書き込み）** | 外部からのソース登録、記事投稿 | セキュリティ/認証/レート制限の設計が必要 |
| **News sitemap** | Google Newsへの配信強化 | ニュースパブリッシャーとしての認定が前提 |
| **A/Bテスト基盤** | 要約形式・スコアリング重みの最適化 | ユーザー行動データの蓄積が先 |
| **クリック/滞在時間によるスコア調整** | ユーザー行動データでスコアリング重みを自動調整 | 十分なアクセスデータが必要 |

### 3.3 スコープ判定の基準

MVPに含めるかどうかは以下の基準で判断した。

| 基準 | 説明 |
|---|---|
| **核心価値への寄与** | aiaiaiの3つの核心価値（一次情報集約・重複統合・実務要約）に直結するか |
| **技術的独立性** | 他の未実装機能への依存なく単独で実装・検証できるか |
| **運用リスク** | 法務・規約違反のリスクがないか（リスクがある場合はMVPで対応必須） |
| **実装コスト** | 1人開発の制約下で現実的な工数か |
| **未指定事項への依存** | 収益モデル・LLM利用先等の未指定事項に依存しないか |

## 5. 技術スタックと選定理由

### 5.1 技術スタック一覧

| 領域 | 技術 | バージョン（推奨） |
|---|---|---|
| フレームワーク | **Next.js**（App Router）+ **TypeScript** | Next.js 14+ / TypeScript 5+ |
| データベース | **PostgreSQL** + **Prisma** | PostgreSQL 15+ / Prisma 5+ |
| UI | **Tailwind CSS** + **shadcn/ui** | Tailwind 3+ |
| 定期実行 | **Vercel Cron Jobs** | vercel.json定義 |
| 検索 | **PostgreSQL FTS** | 組み込み機能 |
| デプロイ | **Vercel** | — |
| テスト | **Vitest** + **Playwright**（E2E） | — |

### 5.2 選定理由

#### Next.js（App Router）+ TypeScript

- **選定理由**: Route HandlersによりWeb標準のRequest/Response APIベースのAPIを実装でき、UIとAPIを**単一リポジトリ**で運用できる。App Routerのサーバーコンポーネントによりデータ取得とレンダリングが効率化される
- **代替案と比較**: Remix（同等の機能だがVercelとの統合度でNext.jsが優位）、Express+React（フロント/バック分離による運用コスト増）
- **MVPでの利点**: 1人開発でフロントとバックエンドを同一リポで管理でき、開発速度を最大化

#### PostgreSQL + Prisma

- **選定理由**: PostgreSQLは全文検索（FTS）を組み込みで持ち、MVP段階で外部検索エンジンが不要。Prismaは型安全なORMとマイグレーション管理を提供し、データモデルの変更を安全に行える
- **代替案と比較**: MySQL（FTSの日本語対応が弱い）、MongoDB（リレーション多用のデータモデルに不向き）、Drizzle ORM（軽量だがエコシステムが小さい）
- **MVPでの利点**: 単一DBで検索まで賄えるため、インフラコストとオペレーションを最小化

#### Tailwind CSS + shadcn/ui

- **選定理由**: ユーティリティファーストで高速にUIを構築でき、shadcn/uiはコピー型コンポーネントのためカスタマイズ性が高い。BtoB適性のある落ち着いたデザインを効率的に実現
- **代替案と比較**: MUI（重量級、カスタマイズにオーバーライドが多い）、Chakra UI（ランタイムCSS-in-JSのパフォーマンス懸念）
- **MVPでの利点**: デザインシステム構築の工数を大幅削減

#### Vercel Cron Jobs

- **選定理由**: `vercel.json`にスケジュールとパスを宣言するだけで定期実行が実現する。Serverless環境での定期実行をゼロコンフィグで導入可能
- **代替案と比較**: GitHub Actions（Vercel外のCI/CD依存）、AWS EventBridge（インフラ管理コスト増）、自前cron（サーバー運用が必要）
- **MVPでの利点**: デプロイ先と定期実行を同一プラットフォームで完結。無料枠で日次実行が可能

#### PostgreSQL FTS（検索）

- **選定理由**: MVPでは追加の検索エンジンを導入せず、PostgreSQLの組み込みFTSで全文検索を実現する。将来的にMeilisearch/Elasticsearch等への差し替えを想定し、検索インターフェースを抽象化
- **代替案と比較**: Meilisearch（高機能だがインフラ追加）、Algolia（SaaS費用）、Elasticsearch（運用コスト高）
- **MVPでの利点**: 追加インフラゼロ、運用コストゼロ

#### Vercel（デプロイ）

- **選定理由**: Next.jsとの深い統合、ゼロコンフィグデプロイ、プレビュー環境の自動生成、Cron Jobs対応。無料枠で個人プロジェクトの運用が可能
- **代替案と比較**: Netlify（Next.js App Routerのサポートが限定的）、AWS Amplify（設定コスト高）、自前VPS（運用負荷大）
- **MVPでの利点**: デプロイ・プレビュー・Cron・ドメイン管理が一箇所で完結
